<a name="بخش-صفر"></a>
## بخشِ صفر — بلوکِ ثابت

این بلوک را **پیش از هر پرامپتی** بفرست. بدونِ آن، نشستِ تازه دوباره
همان پرسش‌ها را می‌پرسد و همان اشتباه‌ها را می‌کند.

```
تو داری رویِ پروژه‌یِ Fitlytix کار می‌کنی — یک برنامه‌یِ مربی‌گریِ ورزشی
که روی cPanel میزبانی می‌شود. زبانِ کاربر فارسی است و راست‌به‌چپ.

هویتِ برند:
  کاربر دو نقش دارد: ورزشکار و مربی.
  شعارِ مربی: «مربی هوشمند…»
  شعارِ اصلی: «بدنت را بشناس. مسیرت را بساز.»
  محورِ معنایی: «حقیقتِ بدن» — واژگانِ «سیگنال» و «اسکان» بر «عکس» مقدم‌اند.

قانونِ نخست، که بر همه چیز مقدم است:
  هیچ عددی ساخته نشود. واقعیت بر امتیاز.
  هر بخش که داده ندارد، جایگاهِ تهیِ صادقانه می‌گیرد که می‌گوید چه چیزی
  کم است — هرگز عددِ قلابی نمی‌گیرد.

قانونِ دوم:
  پیش‌نمونه نخست. هیچ چیز به سایت نمی‌رود تا کاربر نگوید «همین است».

قانونِ سوم:
  هر مرحله پیش از رفتن به مرحله‌یِ بعد تأیید شود. برای هر مرحله یک
  اسکریپتِ فقط‌خواندنی تحویل بده که وضعیت را چاپ کند.

محدودیت‌هایِ محیط، که آزموده شده‌اند:
  سرور پایتون ندارد. فقط Node، و فقط با همان مسیرِ محیطِ مجازیِ ساخت.
  touch tmp/restart.txt برنامه را ری‌استارت نمی‌کند. ری‌استارت فقط از
  cPanel ← Setup Node.js App ← fitlytix-app ← Restart.
  متنی که از ترمینالِ کاربر رونوشت می‌شود اعتبار ندارد — فاصله‌ها در آن
  بی‌صدا حذف می‌شوند. پس هیچوقت بر متنِ کپی‌شده تکیه نکن؛ اسکریپت بنویس
  که متنِ واقعیِ فایل را با نشانه‌یِ «·» به‌جایِ فاصله چاپ کند.
  بارگذاری تنها این پسوندها را می‌پذیرد: png webp jpeg gif txt
  markdown csv html xml css javascript json pdf.  فایلِ .tsx و .zip
  رد می‌شود — پس کدِ سمتِ سرور را با پسوندِ .txt بفرست.
  git در کار نیست. خروجیِ کار: پرونده + وصله + دستور.
  نامِ همه‌یِ پرونده‌ها لاتین باشد.

الگویِ تحویل:
  پرونده‌یِ تازه = کپیِ مستقیم.
  پرونده‌یِ موجود = وصله، هرگز بازنویسیِ کامل (مگر اینکه صریحاً اجازه بدهم).
  وصله‌ها لنگر-محور و خود-بازرسی‌اند: پیش‌نیاز را چک می‌کنند، یکتا هستند،
  پشتیبان می‌گیرند، و در نبودِ هر نشانه کنار می‌کشند بی‌آنکه چیزی بنویسند.

پایگاهِ داده:
  تنها درونِ فرایندِ Node قابلِ دسترسی است (بیرون از آن ERROR 1045).
  هیچوقت نامِ ستون را حدس نزن — نخست DESCRIBE.
  تغییرات فقط افزودنی‌اند؛ چیزی حذف یا تغییرِ نام نمی‌شود.

دیداری:
  داشبورد باید چشمگیر باشد — کارت، نمودار، آیکون.
  جهتِ نمودار در راست‌به‌چپ: کمینه در راست، بیشینه در چپ.
  مقدارِ غیرِمعقول نشانه‌گذاری شود، نه اینکه بی‌صدا مصرف شود.
  امتیازدهی افراطی نکن؛ «عالی» از صدکِ هشتاد آغاز می‌شود.
  جنسیت را برنامه در زمانِ اجرا می‌خواند — هرگز از کاربر نپرس.

پیمایش:
  کاربر-ران باشد و همیشه پیدا. دو دکمه‌یِ گردِ ۴۶ پیکسلی بر لبه‌هایِ اسلاید
  می‌نشینند، نه در حالتِ هاور. در راست‌به‌چپ دکمه‌یِ چپ = بعدی،
  دکمه‌یِ راست = قبلی، و همین‌طور کلیدهایِ ← →.
  نقطه‌ها، شمارنده و دکمه‌یِ توقف می‌مانند.
  هر تب نمایشِ اسلایدیِ خودش را دارد، نه رونوشتی از تبِ دیگر.
```

## بخشِ یک — پایه‌ها

### P01 · نام‌نویسی و ورود

**پیش‌نیاز:** هیچ. نخستین کار.

```
یک برنامه‌یِ ورزشی دارم با دو نقش: ورزشکار و مربی. نام‌نویسی و ورود را
بساز. پس از نام‌نویسی، هر کاربر باید در پایگاهِ داده ردی از خود داشته
باشد و نشستش پایدار بماند. نشست را با کوکیِ امن نگه دار، نه در localStorage.
دو نقش را از همان لحظه‌یِ نام‌نویسی از هم جدا کن — بعداً هر کدام مسیرِ
خودش را می‌رود.
```

**تحویل:** مسیرهایِ `/register` و `/login`، تابعِ نشست، جدولِ کاربران.
**تأیید:** نام‌نویسی کن، خارج شو، دوباره درآی — باید شناخته شوی.

```
ارزیابیِ ورزشکار در پایگاهِ داده ذخیره نمی‌شود. پاسخ‌ها را ماندگار کن.
هر پاسخ باید در جدولِ خودش با کلیدِ پرسش بنشیند، تا بعداً بتوان
تک‌تکِ آن‌ها را بازخواند بی‌آنکه کلِ بسته را باز کنم.

### P07 · APIِ سلامت

```
یک مسیرِ API بساز: GET /api/athlete/health
که سنجه‌هایِ سلامتِ ورزشکارِ کنونی را برگرداند. پیش از هر چیز
DESCRIBE بزن و نامِ ستون‌ها را ببین — حدس نزن. خروجی باید شاملِ
نوعِ سنجه، مقدار، یکا و زمانِ اندازه‌گیری باشد.

> این یکی از آن چیزهایی است که تنها با DESCRIBE به دست می‌آید.

## بخشِ دو — داده‌یِ واقعی و صداقت

### P09 · بررسیِ پایگاهِ داده (فقط‌خواندنی)

این الگو آن‌قدر خوب جواب داد که برایِ هر مرحله تکرارش کردیم.

```
یک اسکریپتِ فقط‌خواندنیِ Node بنویس که پایگاهِ داده را بررسی کند و
چاپ کند:
  ۱. فهرستِ جدول‌ها و شمارِ ردیف‌هایِ هر کدام
  ۲. ساختارِ هر جدولِ مهم (DESCRIBE)
  ۳. نمونه‌یِ واقعیِ چند ردیف
هیچ چیز را تغییر ندهد. پیش از اجرا فقط گذرواژه را از متغیرهایِ محیط
بخواند — نامِ کاربری و گذرواژه را در خروجی چاپ نکند.
اگر هر پرس‌وجویی غیر از SELECT/DESCRIBE/SHOW خواست اجرا شود،
اجازه نده و پیام بده.
```

**یافته‌هایِ کلیدی که این اسکریپت آورد:**

| جدول | ردیف | یادداشت |
|---|---|---|
| `assessments` | ۸ | `athlete_user_id`، answers، score_json |
| `assessment_answers` | ۷۰ | ستونِ کارآمد **`answer_json`**؛ `answer_text`/`answer_number` تهی‌اند |
| `athlete_profiles` | ۸ | کلیدِ اصلی `user_id` |
| `athlete_sports` | ۱ | |
| `manual_health_entries` | ۹ | |
| `health_metrics` | ۹ | ستونِ زمان **`start_time`** |
| `assessment_questions` | ۰ | **تهی** |
| `body_measurements` | ۰ | **تهی** |
| `fitness_metrics` | ۰ | **تهی** |

پاسخ‌هایِ واقعیِ ارزیابی: سن ۳۴، قد ۱۷۴، وزن ۷۴.

### P10 · نه سنجه‌یِ زنده

```
تمامِ سنجه‌هایِ زنده‌یِ ورزشکارِ کنونی را از پایگاهِ داده بخوان و چاپ کن،
هر کدام با مقدار و یکا و زمان. اگر مقداری غیرِمعقول است — مثلاً
چهار گام در روز، یا چهار دقیقه تمرین — آن را نشانه‌گذاری کن،
نه اینکه بی‌صدا مصرفش کنی.
```

**یافته** (ورزشکار `b45d30e8-0435-4371-8ef6-3c13d822f5c8`، همه با `data_origin=live`، همگی در ۲۰۲۶-۱۰-۳۱ ساعت ۰۸:۱۸):

```
وزن            ۷۵ کیلوگرم
چربیِ بدن       ۷ درصد
vo2max         ۵۴
ضربانِ استراحت  ۷۵
HRV            ۷۵ میلی‌ثانیه
خواب           ۷ ساعت
بارِ تمرین      ۷ واحد
زمانِ تمرین     ۴ دقیقه   ← غیرِمعقول، نشانه‌گذاری شود
گام‌ها          ۴          ← غیرِمعقول، نشانه‌گذاری شود
```

> **همه‌یِ نه تا یک برچسبِ زمان دارند.** یعنی نمودارِ روند ممکن نیست —
> یک نقطه روند نمی‌سازد. این کشف، اسلایدِ «روند» را به جایگاهِ تهی تبدیل کرد.

### P11 · مدلِ سه‌لایه

این تصمیم، معماریِ همه‌یِ کارهایِ بعدی شد.

```
می‌خواهم داده‌یِ سلامت را سه لایه نشان بدهم. این سه لایه را تعریف کن،
و برایِ هر کدام بگو چه چیزی در آن جا دارد و چه چیزی هرگز:

  ۱. سنجیده‌ها — مقدارِ خام + یکا + تاریخ. هیچ تفسیری. هیچ امتیازی.
  ۲. جایگاه — نشانگر روی یک بازه‌یِ منتشرشده. این «کجایِ بازه هستم»
     است، نه «چه نمره‌ای گرفتم».
  ۳. ناسازگاری‌ها — کشمکشِ میانِ سنجه‌ها را نشان بده. هرگز میانگین نگیر.

بیرون گذاشته شود: گام‌ها و زمانِ تمرین (هر دو غیرِمعقول‌اند).
جایگاهِ تهیِ صادقانه: دی‌ان‌ایِ تناسب‌اندام، ترکیبِ بدن، روند.
```

**تأییدِ کاربر:** پذیرفته شد.

### P12 · محدوده‌هایِ مرجع

```
یک پرونده‌یِ محدوده‌هایِ مرجع بنویس — src/lib/reference-ranges.ts
که این‌ها را صادر کند:

  refOf(key)
  positionOf(key, value, {sex, age}) → {value, pct, zone, below, above} | null
  inconsistencies(snapshot, ctx) → Finding[]

قانونِ سخت: اگر سن یا جنسیت نباشد، positionOf باید null برگرداند.
هرگز حدس نزند. هرگز پیش‌فرضِ «مرد» نگذارد.

بازه‌ها را در همین پرونده بنشان، با ارجاع به منبعِ منتشرشده.
HRV و بارِ تمرین عمداً نباشند — برایِ آن‌ها مرجعِ معتبر نداریم،
و نداشتنِ مرجع بهتر از مرجعِ ساختگی است.
```

**بازه‌ها:** VO2 ۲۵–۶۰ · ضربانِ استراحت ۴۰–۱۰۰ · خواب ۴–۱۱ ·
چربیِ بدن: مرد ۳–۳۰ / زن ۸–۳۸

**تأییدِ عددی** (مرد، ۳۴ ساله) — این‌ها را اجرا کردیم و درست بودند:

```
VO2 ۵۴       → ۸۲٫۹٪  «عالی»
ضربان ۷۵     → ۵۸٫۳٪  «میانگین»
خواب ۷       → ۴۲٫۹٪  «مطلوب»
چربیِ بدن ۷  → ۱۴٫۸٪  «ورزشکار»
یک ناسازگاری

زن، ۳۴ ساله: چربیِ بدن ۷ → «زیرِ حدِ ضروری»، دو ناسازگاری
```

> **درس:** چهار خطایِ این پرونده تنها با **اجرا کردنش** گرفته شد،
> نه با خواندن. همیشه خروجی را اجرا کن و ببین.

### P23 · تأیید با کامپایلر (الگویِ ارزشمند)

**این ارزشمندترین چیزی است که در این دوره یاد گرفتیم.**

کامپایلرِ واقعی بده:

```
یک محیطِ آزمایش بساز: تایپ‌اسکریپت + ری‌اکت نصب کن، برایِ هر وابستگیِ

وظیفه: خطایی که وصله افزوده باشد. خطاهایی که در هر دو فهرست هستند
مصنوعِ محیطِ آزمایش‌اند، نه ایرادِ کد.
```

**دو خطایِ واقعی که این کار گرفت و بررسیِ دستی ندید:**

  `const athleteId = me?.id ?? demoAthlete.id;` منتقل کردم.
- **یک بند دو بار نوشته شده بود** — `const { latest }` تکراری،
